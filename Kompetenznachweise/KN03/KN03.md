## Phase 1: Infrastruktur, Cloud-Init & Den Flaschenhals verstehen

### Warum sind hohe Latenzen problematisch?

Latenzzeiten von mehreren Sekunden führen zu einer schlechten Benutzererfahrung, da Anwender auf Antworten warten müssen. In modernen Web-Anwendungen werden Reaktionszeiten von wenigen Millisekunden bis höchstens einigen hundert Millisekunden erwartet. Zusätzlich können häufige langsame Anfragen externe APIs unnötig belasten und zu Rate-Limits führen.

## Phase 2: Implementierung Caching

### Erklärung: Cache-Aside Pattern

Beim Cache-Aside Pattern prüft die Applikation zuerst, ob die benötigten Daten bereits im Cache vorhanden sind. Wenn die Daten vorhanden sind, spricht man von einem Cache Hit und die Daten werden direkt aus Redis geladen. Wenn die Daten fehlen, spricht man von einem Cache Miss. Dann lädt die Applikation die Daten aus der langsamen Datenquelle und speichert sie anschliessend im Cache für zukünftige Abfragen.

![Phase 2 - Diagramm](/Kompetenznachweise/KN03/Images/Phase-2_Digramm.png)

### Angepasster Python-Code

```python
def get_crypto_data(coin_symbol):
    cache_key = f"crypto:{coin_symbol}"

    if r:
        cached_data = r.get(cache_key)

        if cached_data:
            print("Cache Hit: Daten wurden aus Redis geladen")
            return cached_data

    print("Cache Miss: Daten nicht im Cache gefunden")
    data = fetch_crypto_history(coin_symbol)

    if r:
        r.setex(cache_key, 60, data)
        print("Daten wurden für 60 Sekunden in Redis gespeichert")

    return data
```

## Phase 4 – Cache Invalidation & Strategie

### TTL Implementierung

Zur Vermeidung von veralteten Cache-Daten wurde beim Speichern der Daten in Redis eine TTL (Time-To-Live) von 15 Sekunden verwendet.

```python
r.setex(cache_key, 15, data)
```

Dadurch werden die gespeicherten Daten nach 15 Sekunden automatisch aus dem Cache entfernt.

### Beobachtung der TTL

Nach dem Ausführen des Scripts wurde die verbleibende Lebensdauer des Cache-Eintrags mit dem Redis-Befehl `TTL` überprüft.

```redis
TTL crypto:BTC
```

Beispiel:

```text
(integer) 13
(integer) 8
(integer) 4
```

Nach Ablauf der Zeit wurde geprüft, ob der Eintrag noch vorhanden ist:

```redis
GET crypto:BTC
```

Ausgabe:

```text
(nil)
```

Dies bestätigt, dass Redis den Cache-Eintrag nach Ablauf der TTL automatisch gelöscht hat.

### Cache Invalidation

Cache Invalidation bezeichnet das Entfernen oder Aktualisieren von veralteten Daten im Cache.

Wenn sich die Daten in der ursprünglichen Datenquelle ändern, könnte Redis weiterhin alte Daten ausliefern. Diese veralteten Daten werden als "Stale Data" bezeichnet.

Durch die Verwendung einer TTL werden die Daten nach einer bestimmten Zeit automatisch entfernt. Beim nächsten Zugriff entsteht ein Cache Miss und die aktuellen Daten werden erneut aus der ursprünglichen Datenquelle geladen.

### Vor- und Nachteile verschiedener TTL-Werte

#### Kurze TTL

Vorteile:

* Daten bleiben aktueller
* Weniger Risiko von veralteten Informationen

Nachteile:

* Mehr Cache Misses
* Häufigere Zugriffe auf die langsame Datenquelle

#### Lange TTL

Vorteile:

* Höhere Performance
* Weniger Last auf der ursprünglichen Datenquelle

Nachteile:

* Höheres Risiko von veralteten Daten
* Änderungen werden später sichtbar

### Fazit

Die TTL ist eine einfache und effektive Methode zur Cache Invalidation. Für Krypto-Kursdaten ist eine eher kurze TTL sinnvoll, da sich die Daten regelmässig ändern und möglichst aktuell bleiben sollen.
