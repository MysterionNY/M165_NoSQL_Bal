## Phase 2: Kanten-Attribute (Relationship Properties)

### Code

```bash
CREATE
  (router:Device {name: 'Main Router'}),
  (sw1:Device {name: 'Switch A'}),
  (sw2:Device {name: 'Switch B'}),
  (db:Server {name: 'Database Server'}),
  (web:Server {name: 'Web Server'}),
  (app:Application {name: 'Online Shop'}),

  (app)-[:DEPENDS_ON {criticality: 'high'}]->(web),
  (app)-[:DEPENDS_ON {criticality: 'high'}]->(db),

  (web)-[:DEPENDS_ON {criticality: 'low'}]->(sw1),
  (db)-[:DEPENDS_ON {criticality: 'low'}]->(sw2),

  (sw1)-[:DEPENDS_ON {criticality: 'high'}]->(router),
  (sw2)-[:DEPENDS_ON {criticality: 'high'}]->(router);
```

### Ausgabe
![Phase 2 Ausgabe](/Kompetenznachweise/KN05/Images/Phase-2_ausgabe.png)

### Erklärung
In Neo4j werden Beziehungen direkt als Kanten zwischen Nodes gespeichert.
In diesem Szenario wurde für jede DEPENDS_ON-Beziehung das Attribut criticality gespeichert. Dadurch kann direkt auf der Beziehung festgelegt werden, ob eine Abhängigkeit kritisch oder weniger kritisch ist.

## Phase 3: Der "Broken AI" Ansatz (Debugging)

### Welchen logischen Fehler hatte die ursprüngliche Query?

Die ursprüngliche Query suchte nach DEPENDS_ON-Beziehungen in die falsche Richtung. Im Graphen zeigt die Beziehung vom Online Shop zum jeweiligen Server, die Query suchte jedoch nach Servern, die auf den Online Shop zeigen. Zusätzlich wurde versucht, das Attribut criticality vom Server-Knoten auszulesen, obwohl es auf der Beziehung gespeichert ist.

### Reparierte Query

```bash
MATCH (app:Application {name: 'Online Shop'})-[r:DEPENDS_ON]->(server:Server)
RETURN server.name AS Server, r.criticality AS Criticality;
```

## Phase 4: Architektur-Reflexion

### Wie müsste das gleiche Modell in SQL aufgebaut werden?

In einer relationalen Datenbank würde man die Geräte, Server und Anwendungen in einer Tabelle speichern. Die Abhängigkeiten müssten in einer separaten Mapping-Tabelle gespeichert werden. Diese Tabelle würde die Fremdschlüssel der beiden verbundenen Einträge sowie das Attribut `criticality` enthalten.

**devices**

| id | name            | type        |
| -- | --------------- | ----------- |
| 1  | Main Router     | Device      |
| 2  | Switch A        | Device      |
| 3  | Switch B        | Device      |
| 4  | Web Server      | Server      |
| 5  | Database Server | Server      |
| 6  | Online Shop     | Application |

**dependencies**

| id | source_id | target_id | criticality |
| -- | --------- | --------- | ----------- |
| 1  | 6         | 4         | high        |
| 2  | 6         | 5         | high        |
| 3  | 4         | 2         | low         |
| 4  | 5         | 3         | low         |
| 5  | 2         | 1         | high        |
| 6  | 3         | 1         | high        |

### PK/FK

```bash
devices.id                PK

dependencies.id           PK
dependencies.source_id    FK -> devices.id
dependencies.target_id    FK -> devices.id
```

### Warum werden tiefe Netzwerkabfragen in SQL langsam, in Neo4j aber schnell?

In SQL müssen Beziehungen über Fremdschlüssel und JOINs miteinander verknüpft werden. Je tiefer man durch ein Netzwerk navigieren möchte, desto mehr JOINs sind notwendig. Dies führt zu einem hohen Rechenaufwand und kann die Abfrage verlangsamen.

Neo4j speichert Beziehungen direkt zwischen den Knoten. Dadurch kann die Datenbank einer Beziehung direkt folgen, ohne zusätzliche JOINs auszuführen. Dieses Konzept nennt sich **Index-Free Adjacency** und ermöglicht sehr schnelle Traversierungen auch über viele Beziehungsebenen hinweg.
