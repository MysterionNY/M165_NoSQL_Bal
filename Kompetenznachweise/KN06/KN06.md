## Phase 2: Die fehlerhafte KI-Tabelle
![Fehlerhafte Ausgabe](/Kompetenznachweise/KN06/Images/Phase2_Fehlerhafte-Ausgabe.png)

### Warum weigert sich Cassandra, die Query auszuführen?

Cassandra kann Daten nur effizient abrufen, wenn die WHERE-Klausel den Partition Key enthält. In der erstellten Tabelle ist trade_id der Partition Key, die Abfrage sucht jedoch nach symbol. Cassandra müsste deshalb alle Partitionen auf allen Knoten durchsuchen und verweigert die Ausführung, um die Performance des verteilten Systems zu schützen.

### Was passiert unter der Haube?

Cassandra verteilt Daten anhand des Partition Keys auf verschiedene Nodes im Cluster. Da symbol nicht Teil des Primary Keys ist, weiß Cassandra nicht, auf welchem Node sich die gewünschten Daten befinden. Die Datenbank müsste deshalb einen vollständigen Scan über alle Partitionen durchführen, was in einem großen Cluster extrem teuer wäre.

## Phase 3: Query-First Design (Modellierung reparieren)

### Korrigiertes Tabellenmodell

```sql
CREATE TABLE ks_app.stock_prices (
    symbol text,
    timestamp timestamp,
    price decimal,
    trade_id uuid,
    PRIMARY KEY (symbol, timestamp)
);
```

### Erklärung

Die Tabelle wurde nach der benötigten Abfrage modelliert. Da das Trading-Dashboard alle Kursdaten für ein bestimmtes Aktien-Symbol abrufen muss, wurde `symbol` als Partition Key gewählt. Der `timestamp` wurde als Clustering Column verwendet, damit die Kursdaten innerhalb einer Partition zeitlich sortiert gespeichert werden.

### Beweis

Die gleiche Abfrage aus Phase 2 funktioniert nun ohne Fehler:

```sql
SELECT * FROM ks_app.stock_prices WHERE symbol = 'AAPL';
```

## Phase 4: Architektur-Reflexion

### Warum ist ALLOW FILTERING ein Anti-Pattern?

`ALLOW FILTERING` zwingt Cassandra dazu, Daten zu durchsuchen, die nicht gezielt über den Partition Key gefunden werden können. In einer grossen, verteilten Cassandra-Datenbank bedeutet das, dass viele Partitionen oder sogar viele Nodes im Cluster durchsucht werden müssen.

Das zerstört die Performance, weil Cassandra nicht mehr direkt weiss, wo die Daten liegen. In produktiven Systemen mit sehr vielen Daten, wie zum Beispiel bei Netflix oder Spotify, kann so eine Abfrage extrem langsam werden und unnötig viele Server-Ressourcen verbrauchen.

### Unterschied zwischen Partition Key und Clustering Column

Der **Partition Key** bestimmt, auf welchem Node beziehungsweise in welcher Partition die Daten gespeichert werden. In meinem korrigierten Modell ist `symbol` der Partition Key, weil die Abfrage nach einem bestimmten Aktien-Symbol sucht.

Die **Clustering Column** bestimmt die Sortierung innerhalb einer Partition. In meinem Beispiel ist `timestamp` die Clustering Column, damit alle Kursdaten eines Symbols zeitlich sortiert gespeichert und abgefragt werden können.

### Fazit

Cassandra muss nach den geplanten Abfragen modelliert werden. Deshalb wurde die Tabelle so angepasst, dass `symbol` direkt im Partition Key enthalten ist. Dadurch kann Cassandra die Daten effizient finden, ohne `ALLOW FILTERING` oder einen teuren Scan über viele Partitionen zu benötigen.
