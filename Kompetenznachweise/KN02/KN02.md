### Modellierung

MongoDB ist eine dokumentenorientierte NoSQL-Datenbank und unterscheidet sich stark von relationalen SQL-Datenbanken.  
Während relationale Datenbanken Daten häufig stark normalisieren und auf mehrere Tabellen verteilen, versucht MongoDB Daten möglichst zusammenhängend in einem Dokument zu speichern.

Das Ziel in MongoDB ist sogenannte **Data Locality**.  
Daten, die häufig gemeinsam gelesen werden, sollen auch gemeinsam gespeichert werden. Dadurch können komplexe Joins und mehrere Abfragen vermieden werden.

#### Referenzielle Integrität

Im Gegensatz zu relationalen Datenbanken überprüft MongoDB Fremdschlüsselbeziehungen nicht automatisch.  
Die Applikation selbst ist dafür verantwortlich, dass Beziehungen zwischen Dokumenten korrekt bleiben.

Dadurch kann beispielsweise ein Dokument auf eine ID verweisen, die gar nicht existiert.

#### Normalisierung und Redundanzen

In relationalen Datenbanken wird oft stark normalisiert, um doppelte Daten zu vermeiden.  
MongoDB verfolgt häufig den gegenteiligen Ansatz und erlaubt bewusst Redundanzen.

Dadurch können Daten schneller gelesen werden, da weniger Verknüpfungen notwendig sind.

Beispielsweise kann eine Adresse direkt in einem Dokument gespeichert werden, anstatt dafür eine separate Collection zu verwenden.

### Modellierungstechniken in MongoDB

MongoDB bietet verschiedene Möglichkeiten Beziehungen abzubilden.

##### Embedding (Einbettung)

Beim Embedding werden zusammengehörige Daten direkt in ein Dokument eingebettet.

Beispiel:

```json
{
  "title": "Spaghetti Carbonara",
  "ingredients": [
    {
      "name": "Spaghetti",
      "amount": 400,
      "unit": "g"
    }
  ]
}
```

Vorteil:

* Schnelleres Lesen
* Weniger Abfragen notwendig
* Bessere Performance

Nachteil:

* Teilweise Redundanzen

##### Referenzen

Bei Referenzen werden Beziehungen ähnlich wie in SQL über IDs hergestellt.

Beispiel:

```json
{
  "recipe_id": "123",
  "ingredient_id": "456"
}
```

Vorteil:

* Weniger doppelte Daten

Nachteil:

* Zusätzliche Lookups notwendig
* Schlechtere Performance bei vielen Verknüpfungen

### Fazit

MongoDB bevorzugt dokumentenorientierte Datenmodelle mit Embedding und Denormalisierung.
Dadurch können Daten schneller gelesen werden und die Anzahl komplexer Joins wird reduziert.

Für Anwendungen mit vielen Lesezugriffen eignet sich dieses Vorgehen besonders gut.

## MongoDB Übersicht

MongoDB ist eine dokumentenorientierte NoSQL-Datenbank.  
Die Daten werden nicht in Tabellen gespeichert, sondern in sogenannten Collections mit JSON-ähnlichen Dokumenten.

Jedes Dokument besitzt automatisch ein Feld namens `_id`, welches als Primärschlüssel dient.  
Falls kein `_id` Feld angegeben wird, erstellt MongoDB dieses automatisch.

### Verbindung mit MongoDB

Beispiel:

### CRUD Operationen

CRUD steht für:

* Create
* Read
* Update
* Delete

### Read (Lesen)

Dokumente können mit `find()` abgefragt werden.

Beispiel:

```js
db.recipes.find()
```

Mit Filter:

```js
db.recipes.find({ difficulty: "Easy" })
```

### Insert (Einfügen)

Ein einzelnes Dokument hinzufügen:

```js
db.recipes.insertOne({
  "title": "Spaghetti Carbonara",
  "difficulty": "Medium",
  "prep_time_min": 25
})
```

Mehrere Dokumente hinzufügen:

```js
db.recipes.insertMany([
  { "title": "Carbonara" },
  { "title": "Pfannkuchen" }
])
```

### Update (Aktualisieren)

Ein Dokument aktualisieren:

```js
db.recipes.updateOne(
  { title: "Carbonara" },
  {
    $set: {
      difficulty: "Easy"
    }
  }
)
```

### Delete (Löschen)

Ein Dokument löschen:

```js
db.recipes.deleteOne({
  title: "Carbonara"
})
```

### Aggregationen

Mit Aggregationen können komplexe Abfragen erstellt werden.
MongoDB verwendet dafür sogenannte Pipelines.

Eine Pipeline besteht aus mehreren Stages, welche nacheinander ausgeführt werden.

Beispiel:

```js
db.orders.aggregate([
  {
    $match: {
      size: "medium"
    }
  },
  {
    $group: {
      _id: "$name",
      totalQuantity: {
        $sum: "$quantity"
      }
    }
  }
])
```

### Wichtige Aggregation-Stages

| SQL      | MongoDB  |
| -------- | -------- |
| WHERE    | $match   |
| GROUP BY | $group   |
| SELECT   | $project |
| ORDER BY | $sort    |
| LIMIT    | $limit   |
| JOIN     | $lookup  |

## Lookups (Joins)

MongoDB unterstützt Joins über den Aggregation-Stage `$lookup`.

Damit können Daten aus mehreren Collections zusammengeführt werden.

Beispiel:

```js
{
  $lookup: {
    from: "ingredients",
    localField: "ingredient_id",
    foreignField: "_id",
    as: "ingredient"
  }
}
```

Der `$lookup` verbindet dabei Dokumente anhand gemeinsamer IDs ähnlich wie ein SQL Join.

### Fazit

MongoDB bietet flexible Möglichkeiten zur Speicherung und Verarbeitung von Daten.
Neben einfachen CRUD-Operationen ermöglichen Aggregationen und Lookups auch komplexe Datenabfragen über mehrere Collections hinweg.

## MongoDB Skalierung

### Skalierung in MongoDB

MongoDB wurde von Anfang an als verteiltes System entwickelt.  
Die Datenbank besitzt bereits im Kern Mechanismen, um Daten automatisch auf mehrere Server zu verteilen.

Dadurch kann MongoDB grosse Datenmengen und hohe Last besser skalieren als viele klassische relationale Datenbanken.

### Data Locality

In MongoDB gilt das Prinzip der sogenannten **Data Locality**.

Das bedeutet:

> Daten, die häufig gemeinsam verwendet werden, sollen auch gemeinsam gespeichert werden.

Dadurch müssen weniger Daten über das Netzwerk zwischen verschiedenen Servern übertragen werden.

### Denormalisierung

MongoDB verwendet häufig den Ansatz der Denormalisierung.

Dabei werden Daten bewusst mehrfach gespeichert, um schnelle Lesezugriffe zu ermöglichen.

Beispiel:

Bei einer Bestellung können Benutzerinformationen und Produktpreise direkt in der Bestellung gespeichert werden.

Vorteile:

- Schnellere Abfragen
- Weniger komplexe Joins
- Bessere Skalierbarkeit

Nachteil:

- Redundante Daten
- Höherer Speicherverbrauch

### JOINS und $lookup

In relationalen Datenbanken werden Daten häufig über Joins zusammengeführt.

Verteilte Joins sind jedoch sehr langsam, da Daten zwischen mehreren Servern ausgetauscht werden müssen.

MongoDB versucht deshalb, klassische Joins möglichst zu vermeiden.

Der Aggregation-Stage `$lookup` existiert zwar, gilt jedoch eher als Ausnahme oder „Notlösung“ und nicht als Standardvorgehen.

### Warum MongoDB gut skaliert

MongoDB skaliert gut, weil:

- Daten lokal gespeichert werden
- weniger Joins notwendig sind
- Daten bereits vollständig in einem Dokument vorliegen
- Netzwerkkommunikation reduziert wird

Dadurch können Abfragen deutlich effizienter ausgeführt werden.

### Replikation und Sharding

MongoDB unterstützt verschiedene Skalierungstechniken.

#### Replikation

Bei der Replikation werden Daten auf mehrere Server kopiert.

Vorteile:

- Höhere Ausfallsicherheit
- Backup bei Serverausfällen
- Bessere Verfügbarkeit


#### Sharding

Beim Sharding werden Daten auf mehrere Server aufgeteilt.

Dadurch können:

- grössere Datenmengen verarbeitet werden
- Lasten verteilt werden
- Abfragen parallel ausgeführt werden

### Fazit

MongoDB wurde speziell für horizontale Skalierung entwickelt.  
Durch Denormalisierung, Data Locality und die Vermeidung komplexer Joins kann MongoDB grosse Datenmengen effizient verarbeiten und über mehrere Server skalieren.
